# A4: Error codes and error behaviour, v2.56.0 → 2-dev `0855cd70f`

Scope: the error catalogue (`lib/kerror/codes/*.json`), the error classes (`lib/kerror/errors/*`), `kerror` itself (`lib/kerror/index.ts`), how errors reach a response (`KuzzleRequest.setError`, `RequestResponse`, funnel wrapping, stack stripping), and the kerror call sites across `lib/`.
BASE = `$S/base` (tag `v2.56.0`), HEAD = `$S/head` (`0855cd70f`). Line numbers refer to those trees. Scripts and probes are in `$S/errors-work/` (`extract.py`, `probe.js`, `*-calls.tsv`).

## Summary: top risks first

1. **`kerror` decides differently which trailing placeholder is an "options" object (E-01, not recorded anywhere).** BASE used `_.isPlainObject`. HEAD uses `safeObject.isPlainObject`, which is `Object.prototype.toString.call(o) === "[object Object]"`, so it also matches **class instances**. When the last placeholder is a class instance, HEAD now takes it out of the placeholders: the message keeps a literal `%s` and `props` loses the value. If the instance has a `message` property, that property **replaces the error message**. I confirmed this by running both `dist/` builds. This reaches public APIs: `context.kerror.get/getFrom/reject` (plugins) and `app.errors.get/getFrom/wrap` (Backend apps). A heuristic scan found no in-tree call site that passes a class instance last.
2. **A native controller's internal crash has a new id (E-02, intended, TD-21/TD-27, #2709).** When a native controller throws anything that is not a `KuzzleError`, the client used to get `plugin.runtime.unexpected_error` (`0x04020002`, `PluginImplementationError`, message "Caught an unexpected plugin error: …\nThis is probably not a Kuzzle error…"). It now gets `core.fatal.unexpected_error` (`0x00000001`, `InternalError`, "Caught an unexpected error: ….").
   - The status is still 500.
   - Plugin controllers and every pipe path are unchanged.
   - The error pipes (`<ctrl>:error<Action>`, `request:onError`) also see the new id.
3. **Two ids that could never be reached now surface (E-03, E-04, intended, step 12 K5).**
   - While Redis is disconnected, every cache command used to answer `core.fatal.unexpected_error` with status 500. It now answers `services.cache.not_connected` (`ServiceUnavailableError`) with **status 503**.
   - Elasticsearch `es_rejected_execution_exception` used to answer `core.fatal.unexpected_error`. It now answers `services.storage.too_many_operations` (`ExternalServiceError`). The status is still 500.
4. **`admin:dump` is stricter (E-07, #2665, after v2.56.0).** The suffix must match `^[A-Za-z0-9_-]{0,64}$`. Anything else is rejected with a bare `BadRequestError` that carries **no `id` and no `code`**.
   - Side effect not recorded anywhere: automatic "handled error" dumps build their suffix from the error message with no length cap. So with `dump.enabled` on, most of them now fail with an unhandled rejection. Under `NODE_ENV=development`, that rejection shuts Kuzzle down.
5. **Catalogue: the only change is the two `invalid_openapi_schema` codes removed by TD-77 (E-05).** I confirmed on BASE that nothing raises them: no reference in `lib/` or `dist/`. The last raise was removed in `fd5601523` (#2271, shipped in 2.17.0, 2022). No other id, code, class, status, message or deprecated flag changed, and the generated doc tables differ only by those two rows.
6. The rest is low severity. Crashes that used to surface as a `TypeError` (usually wrapped as an unexpected error) now raise a documented, more specific error: E-06, E-12, E-13, E-14, E-16, E-17. On top of that come small message and shape changes (E-08 to E-11, E-15, E-18) and TypeScript declaration changes on the exported error classes (E-10).

Checked and **unchanged**:
- `KuzzleError.toJSON()` shape: `code, id, message, props, stack, status`, plus `errors, count` for `PartialError`.
- `name` (still `constructor.name`) and the status of every class.
- `KuzzleRequest.setError`: a non-`KuzzleError` still becomes an `InternalError` without id or code, and a non-Error is still refused.
- `RequestResponse` error serialisation.
- Stack stripping, done by the protocols and `entryPoint`. BASE's `router.js` call was a no-op on a `KuzzleRequest`, so removing it in HEAD changes nothing.
- The `%s` order in every message template. The catalogue messages are byte-identical, and the argument diff below found no reordering.

### Placeholder arguments (item 4)

I diffed the argument list of every `kerror.get/reject/getFrom` call site between BASE and HEAD, grouped by file and resolved id. Apart from the rows above, every difference is a rename of a local variable with the same meaning (`e.message` becoming `cause.message`, `encoding[1]` becoming `charset`, and so on). Two differences reach only the logs:
- `protocol.runtime.invalid_connection` in `router.removeConnection` now logs `JSON.stringify(requestContext)` rather than `requestContext.context`, which was `undefined`.
- The `security.role.unknown_action` hint now reads `controller._actions`. BASE read `__actions`, which was `undefined`, so the "did you mean" suggestion is now populated.

No template changed and no argument order changed.

### Found along the way: pre-existing, identical in BASE and HEAD

- `lib/core/statistics/statistics.ts:27` wraps `("services", "stats")`, but the subdomain is named `statistics`. So `server:getLastStats` and `server:getStats` with statistics disabled answer `core.fatal.unexpected_error` ("…services.stats.not_available.") in both versions, not `services.statistics.not_available`. This is not a regression, but it is the same kind of misspelled-id bug as E-03 and E-04, and it is still there.
- The message of `plugin.strategy.strategy_not_found` ("Cannot remove strategy…") is now reused for lookups (E-13).
- Outside the error surface, recorded in step 12: `auth:getCurrentUser` for the anonymous user now returns `strategies: []` instead of `[[]]`, and `global.kuzzle.id` is now set, which fills the `node` field of realtime notifications. These belong to A3 and A5.

## What I could not check

- **Runtime reachability of E-06, E-16 and E-17 through each protocol.** For example, whether HTTP or MQTT deliver `body: null` or `{}` for an empty body. I inferred this from the code and did not run it in a cluster. No functional test was run.
- **Completeness of the call-site extraction.** The extractor (`errors-work/extract.py`) resolves wrapper variables of the form `const x = kerror.wrap(d, s)` or `require(...).wrap(d, s)`, plus the literal three-argument form. It misses ids passed through a variable (for example `errorId` in `pluginsManager.resolveEventHandler`, which I checked by hand) and inline `wrap(...).get(...)`. I did a second pass on the direct `new XxxError(` constructions; the only new one is in `dumpGenerator`.
- **E-01 in the wild.** I did not audit third-party plugins or apps for class-instance placeholders. The scan of HEAD's own call sites found none, but it only covered expressions that are not string-like (`errors-work` scan).
- **Behaviour changes that do not go through a kerror call** (validation types, `getArrayOrCsv` and the other request getters, `hotelClerk`'s null-action paths). I only covered the error ids they raise. Input-acceptance changes belong to A3.
- **I did not run BASE functional tests against HEAD.** The probes cover only `kerror` and the error classes, run through the two `dist/` builds.
